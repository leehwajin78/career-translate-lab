### G-01. 기술 스택 방향

**우선순위:** 🔴 최우선 — 이 결정이 G-02~G-05 전체에 영향을 줌

**현재 상황:**
- 구현: Vite + React + Zustand (순수 클라이언트)
- SRS 계획: Next.js App Router + Server Actions + Prisma

**선택지:**

| 옵션 | 설명 | 장점 | 단점 |
| :--- | :--- | :--- | :--- |
| **A. Vite 유지** | 현 코드베이스 그대로. 백엔드는 Supabase Edge Function 또는 별도 API 서버 | 현재 코드 자산 보존, 추가 학습 불필요 | 서버 액션 없어 API 구조 별도 설계 필요 |
| **B. Next.js 마이그레이션** | SRS 설계대로 전환 | SRS 문서와 정합, Server Actions 활용 | 현재 구현 전체 재작성 비용 |
| **C. Vite + Supabase 직접 연동** | Vite 유지하되 Supabase JS SDK로 직접 DB 연동 | 코드 재작성 최소화, DB 영속성 확보 | AI API 키는 클라이언트에 노출 위험 |

**결정 완료:** _(미결)_

### G-02. 데이터 저장 레이어

**우선순위:** 🔴 최우선 — 실제 고객 데이터 운영 전 필수

**현재 상황:**
- 모든 데이터(리드, 멤버, 코칭 답변)가 브라우저 localStorage에만 저장
- 기기/브라우저 변경 시 데이터 유실
- 관리자가 고객 데이터를 다른 기기에서 볼 수 없음

**선택지:**

| 옵션 | 설명 | 전제 조건 |
| :--- | :--- | :--- |
| **A. localStorage 유지** | 파일럿 기간 동안만 유지, 실제 고객 수용 전 전환 | 파일럿 종료 시점 명확히 정의 |
| **B. Supabase Free 연동** | Zustand → Supabase로 데이터 레이어 교체 | G-01 결정 필요 |
| **C. 중간 방안: 이중 저장** | localStorage + Supabase 동시 저장 (점진적 전환) | 코드 복잡도 증가 |

**결정 완료:** _(미결)_

### G-03. AI 연동 방식

**우선순위:** 🔴 최우선 — 서비스 핵심 가치(AI 브랜드 진단)와 직결

**현재 상황:**
- 무료 진단: `analyzeFree()` 로컬 알고리즘 (규칙 기반 점수 산출)
- 실제 AI API 호출 없음

**선택지:**

| 옵션 | 설명 | 비용 | 전제 조건 |
| :--- | :--- | :--- | :--- |
| **A. 로컬 알고리즘 유지** | 파일럿 기간 동안 현행 유지 | 무료 | 알고리즘 품질 개선 필요 |
| **B. Gemini API 연동** | SRS 계획대로 | 무료 티어 (제한 있음) | 서버 사이드 API 키 관리 필요 (G-01 연동) |
| **C. Claude API 연동** | Anthropic Claude 사용 | 유료 | 서버 사이드 필요 |
| **D. B+A 혼합** | 로컬 알고리즘으로 빠른 결과 → 별도 AI로 심화 리포트 생성 | Gemini 무료 티어 | 구현 복잡도 증가 |

**추가 결정 필요:**
- AI 생성 리포트를 고객에게 즉시 표시할 것인가, 관리자 검수 후 표시할 것인가?
